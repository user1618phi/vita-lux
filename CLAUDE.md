# Vita Lux — интернет-магазин сантехники

## Команды
- Разработка: `pnpm dev` (:8000)
- Типы: `pnpm typecheck` — ОБЯЗАТЕЛЬНО после серии правок
- Линт: `pnpm lint`
- Тесты: `pnpm test` (node:test)
- Локали: `node scripts/check-kk-glyphs.mjs` — паритет ru/kk, глифы, пустые переводы
- Миграции: `pnpm db:generate` → `pnpm db:migrate`
- Данные: `pnpm db:seed` (мок → БД), `pnpm db:parity` (сверка mock vs db)
- Админ: `pnpm db:admin -- --user <логин> --role owner`

## Раскладка — монорепо
```
apps/web      витрина, Next + next-intl, порт 8000
apps/admin    админка, Next без next-intl, порт 8001
packages/core чистый домен: без Next, без React
packages/db   schema, client, drizzle.config, миграции
packages/data репозиторий каталога, настройки, мок-контент
packages/ui   токены @theme и тема (ThemeScript)
packages/i18n локали ru/kk и единственный загрузчик к ним
scripts/      seed, parity, create-admin, проверка глифов
```
Осталось: `apps/api` — общий бэк, его будут звать ещё мобилка и
1С/маркетплейсы. Пока оба фронта ходят в БД напрямую через `@vita/data`.

Пакеты отдают ИСХОДНЫЙ TypeScript, без шага сборки — за это `next.config.ts`
КАЖДОГО приложения обязан держать их в `transpilePackages`.

`@types/react` обязан быть и в корневых devDependencies, не только в
приложениях: типы `next` ищут React по дереву каталогов, и без корневой копии
`ScriptHTMLAttributes` не резолвится — `next/script` начинает ругаться на
несуществующий проп `src`.

Экспорты пакетов — только subpath (`@vita/core/pricing`), НИКОГДА не barrel
`index.ts`: общий бочонок утащит `crypto` в браузерный бандл клиентского
компонента, который просил всего лишь `format`.

Зависимость смотрит из UI в домен, не наоборот. `StockState` и `IconName`
живут в `@vita/core`, компоненты их реализуют. `PATHS` в `Icon.tsx` закрыт
`satisfies Record<IconName, ReactNode>` — не меняй на аннотацию
`: Record<string, ReactNode>`: именно так `IconName` однажды выродился в
`string` и перестал ловить опечатки в именах иконок.

## Стек
Next.js 15 App Router, TypeScript strict, Tailwind CSS v4 (`@theme`),
PostgreSQL + Drizzle, Zod, sharp.
Medusa и Meilisearch НЕ используются — сознательное решение: на 55–200 SKU
это второй сервис и вторая админка без выигрыша. Пересмотреть на ~500 SKU.
Server Components по умолчанию. Клиентские — только там, где нужна
интерактивность.
Запрещены UI-библиотеки со своим визуальным стилем (MUI, Ant, Chakra,
Bootstrap). Radix UI Primitives разрешён — только за поведение, без стилей.

## Данные каталога — КРИТИЧНО
Страницы читают каталог ТОЛЬКО через `@vita/data/repo`, никогда напрямую из
`@vita/data/content/catalog` или из БД. Репозиторий отдаёт `name` уже локализованным —
не ищи название по хендлу в компонентах.
Источник переключается через `CATALOG_SOURCE` (`mock` по умолчанию, `db`).
`@vita/data/repo` помечен `server-only`: импорт из клиентского компонента утащит
в браузер весь каталог и драйвер БД.
Корзина и избранное хранят снапшот товара, а не джойн по каталогу; серверный
экшен `resolveHandles` перепроверяет цену и наличие при монтировании.

Любая мутация в админке ОБЯЗАНА звать `revalidateTag(CATALOG_TAG)` и
`revalidateTag(productTag(handle))`. Иначе правка цены не видна на сайте.

## Mobile-first
Более 75% трафика мобильный. Проверяй на 390px первым, потом расширяй.
Размер шрифта в полях ввода строго 16px — иначе iOS зумит страницу.

Нижняя панель вкладок прячется при скролле вниз и возвращается при скролле
вверх (`useHideOnScrollDown`). Её высота публикуется в `--tabbar-h`, а
состояние — атрибутом `data-tabbar` на `<html>`. ВСЁ, что закреплено над
панелью (липкая кнопка «В корзину», плавающая кнопка WhatsApp), обязано
отсчитываться от `--tabbar-h`, а не от константы 56px: иначе при спрятанной
панели элемент зависает с пустой полосой под собой.

Закреплённые полосы НЕ выезжают снизу (`translateY(120%)`): такая анимация
проводит элемент сквозь панель вкладок, и полсекунды видно наложение с
обрезанным низом. Появление — проявлением и сдвигом сверху вниз.

У `<header>` есть `transform` — мобильная полоса с телефоном уезжает при
скролле. Поэтому ВНУТРИ шапки не должно быть ничего с `position: fixed`:
ненулевой transform делает элемент точкой отсчёта для fixed-потомков, и такой
элемент растянется на шапку, а не на экран. Мобильное меню по этой причине
лежит снаружи `<header>`, рядом с ним во фрагменте.

Плавающая кнопка WhatsApp (`WhatsAppFab`) показывается, пока на экране нет ни
одной настоящей кнопки канала. Следит по атрибуту `data-wa-cta`: вешай его на
обёртку каждой новой кнопки WhatsApp, иначе рядом с ней всплывёт дубль.

YOU MUST проверять казахские глифы ә ө ұ ү қ ң ғ һ і после правки kk-локали
(`node scripts/check-kk-glyphs.mjs`).
Казахский текст на 10–20% длиннее русского — проверяй, что верстка не ломается.
Исключение: админка — только русский. Раньше ради этого её держали вне сегмента
`[locale]` и городили спецслучай в matcher; теперь она отдельное приложение
(`apps/admin`) и next-intl там не подключён вовсе. В `apps/web` маршрута
`/admin` больше НЕТ — не добавляй его обратно.

Локали лежат в `packages/i18n/messages` и читаются ТОЛЬКО через
`@vita/i18n/load`. Не собирай путь к ним относительно своего файла: так уже
делали три модуля, при переезде пути ломались, а в мок-каталоге чтение обёрнуто
в try/catch — поломка выглядела не как ошибка, а как товары, у которых вместо
названия показывался хендл. Импорт локалей статический, чтобы пропавший файл
падал на сборке. `@vita/i18n/paths` — отдельная точка входа для Node-скриптов:
webpack разбирает `new URL(..., import.meta.url)` и на каталоге спотыкается,
поэтому её нельзя тянуть в код приложения.

## Админка на публичных деплоях — КРИТИЧНО
`ADMIN_ENABLED` работает fail-closed: приложение админки отвечает только при
значении ровно `1`, любое другое (включая отсутствие) — 404 на КАЖДЫЙ маршрут,
вместе с POST Server Actions.
Гейт обязан жить в `apps/admin/src/middleware.ts`: Server Actions диспатчатся по
id через POST и выполняются ДО рендера layout, поэтому `notFound()` в layout
мутацию не остановит. Проверка в `layout.tsx` — второй рубеж, не замена.
Отсюда же минимальная версия Next: до 15.2.3 CVE-2025-29927 позволяет обойти
middleware заголовком `x-middleware-subrequest`, то есть снять этот гейт. Не
понижай Next ниже 15.5.x.

Кука сессии админки ставится с `path: "/"`. Не возвращай `/admin`: приложение
больше не живёт по этому префиксу, и браузер просто перестанет присылать куку —
вход молча сломается. (Заодно это чинило старый баг: кука ставилась на `/admin`,
а удалялась на `/`, поэтому выход её не убирал.)

## Токены
Компоненты используют ТОЛЬКО семантические токены
(text-primary, surface-page, border-control и т.д.),
никогда не примитивы напрямую.

## Тема — КРИТИЧНО
Имена цветов — это РОЛИ, а не литеральные цвета. `ink` = «максимально
контрастный текст», `porcelain` = «фон страницы», `glaze` = «поверхность,
которая ложится на ink». Под `html[data-theme="dark"]` те же роли указывают на
другие хексы, поэтому `text-ink` и `bg-porcelain` верны в обеих темах и
`dark:`-вариантов в компонентах нет и быть не должно.
Следствие: в тёмной теме `--ink` — светлый, а заливка первичной кнопки —
кремовая. Подпись на такой заливке — ВСЕГДА `--action-primary-text`
(и никогда `#fff` и не `--text-on-dark`).

Полярность не переворачивают только те роли, чей фон — фотография, а не
поверхность темы: `--text-on-dark`, `--text-on-light`, `--surface-on-photo*`,
`--text-on-photo` и вариант кнопки `onPhoto`. Их и используй для всего, что
лежит поверх снимка, скрима или блока basalt.

Тему ставит инлайн-скрипт (`@vita/ui/theme/script`) в `<head>` до первой
отрисовки: `data-theme` на `<html>`, ключ `vl-theme` в localStorage.
Умолчание — ТЁМНАЯ (`DEFAULT_THEME`), системная тема сознательно НЕ
учитывается: витрина должна выглядеть одинаково у всех, кто пришёл впервые.
`prefers-color-scheme` не должен появиться ни в скрипте, ни в `themeColor` —
иначе адресная строка на мобильном разъедется с фоном страницы.
`.vl-when-light` / `.vl-when-dark` переключают
содержимое без React-состояния (иначе тумблер моргает на каждой загрузке).
Логотип цвет берёт из `--logo-mark` / `--logo-text`: днём золото
(`--brass-text` #83602f, 5.5:1 — заливочная латунь #a97c50 для надписи не
проходит), ночью белый. `variant="light"` — только для логотипа на постоянно
тёмном блоке (подвал), там белый в обеих темах.
Знак живёт в двух местах: `components/ui/Logo.tsx` и `public/favicon.svg`.
Растровые иконки НЕ правь руками — `node scripts/gen-icons.mjs` пересобирает
их из favicon.svg.
Фотографии помечай классом `vl-photo` — в тёмной теме им снимается яркость.
НИКОГДА не вешай фильтр на `img` целиком: логотип Kaspi — тоже `<img>`,
перекрашивать чужой товарный знак нельзя.
Проверка после правок цвета: обход DOM с расчётом контраста в обеих темах
(см. отчёт в истории задачи), плюс скриншоты на 390px.

## Заказы и платежи — КРИТИЧНО, не ломать
Цены НИКОГДА не принимаются от клиента: браузер шлёт хендлы и количества,
сервер пересчитывает всё сам. `order_item` хранит снапшот имени и цены.
Реф-код генерируется на сервере (`@/lib/order/ref`), идемпотентность — по
`idempotency_key` с unique-индексом.
НИКОГДА не логируй payload заказа и платежа: там персональные данные.
Halyk ePay + Kaspi Pay/Kaspi Red — договор с Kaspi Red есть; сроки рассрочки
берутся из `setting`, не хардкодь.

## Данные и право
Персональные данные граждан РК по закону хранятся на серверах в Казахстане.
Сейчас БД вне РК — это осознанный временный компромисс. Поэтому:
имя, телефон и адрес шифруются (`@/lib/crypto`), рядом лежит только солёный
хеш для поиска, и все ПД собраны в трёх колонках `order` — чтобы переезд в
КЗ-хостинг был одним скриптом. Согласие пользователя обязательно, версия
хранится в заказе (`@/lib/order/consent`).

## X2pos — склад и касса владельца
Учёт (остатки, цены, фото) ведётся в X2pos, сайт его только читает. Обратно
уходят продажи, чтобы остаток списывался.

Живой API БОГАЧЕ документации v1.6, и PDF местами врёт. Проверено на боевом
аккаунте: `/api/products` отдаёт `image_url` (в PDF фото только у категорий);
`variations` — объект с ключами-id, а НЕ массив; есть недокументированный
`GET /api/orders` с `form_guid` и `external_order_id`; `/api/stock` требует
явный `branch_id` — с `all` или без параметра молча возвращает пустой массив.
`image_thumb_url` бесполезен: миниатюра больше оригинала, поэтому берём
`image_url` и жмём сами через `processPhoto`.

Кто чем владеет — КРИТИЧНО. X2pos владеет фактом существования товара,
артикулом, ценой, остатком и фото. Админка владеет handle, названиями ru/kk,
описанием, категорией, фасетами и SEO. Синк НЕ ИМЕЕТ ПРАВА трогать второе:
названия в X2pos для витрины непригодны (36 позиций там называются просто
«Унитаз»), поэтому новые товары приезжают как `draft` в неактивную категорию
`x2pos-inbox` и на витрину не попадают, пока человек не заполнит карточку.
Уникален только артикул; `variant.sku` уникальным делать по-прежнему нельзя,
ключ синхронизации — `variant.externalId` (частичный unique-индекс).

Цены. Синк пишет строку `mode: "auto"` и ОБЯЗАН закрыть предыдущую открытую
(`validTo = now()`) — та же конвенция, что в админке. Пока действует строка
`mode: "manual"`, синк цену НЕ ТРОГАЕТ: обновляет только `wholesaleKzt` и
`baseRetailKzt` прямо в ней (это справочные числа из X2pos, а не решение
магазина). `createdBy` синк не заполняет — иначе `seed.ts` посчитает товар
правленным руками. Акция на срок — строка с `validTo` в будущем: по окончании
окна побеждает базовая, крон для «вернуть цену» не нужен.

Витрина выбирает цену через `DISTINCT ON (variant_id) … ORDER BY valid_from
DESC` в `db.source.ts`. Не возвращай обычный `leftJoin` по `priceIsCurrent`:
при двух действующих строках (а это ровно случай акции) join размножает товар,
порядок не задан, и цена выбирается произвольно.

Остатки. Резерва в X2pos НЕТ, и он разрешает уходить в минус
(`settings_negative_stock_allowed = 1`). Защита — буфер `stock.bufferQty`:
`qty >= буфера` → «в наличии», иначе «под заказ». `qtyToStockState` НИКОГДА не
возвращает `out` — он блокирует корзину, а товар при нуле всё ещё можно
заказать; `out` только для архивных. Отсутствие строки в `/api/stock` — это
ноль, а вот ПУСТОЙ ответ целиком — признак неверного `branch_id`, и клиент на
него бросает, иначе один прогон обнулил бы весь каталог.

Заказы. Продажа уходит со статусом `issued` — остаток списывается сразу.
Строка `x2pos_outbox` пишется В ТОЙ ЖЕ транзакции, что и заказ: состояния
«заказ принят, а склад о нём не узнает» не существует. `form_guid` —
идемпотентность на стороне X2pos, перед повтором очередь ищет заказ по нему
через `GET /api/orders`, иначе можно продать товар дважды. Отмена заказа
обязана вызвать возврат, иначе склад недосчитается товара. Создать продажу при
ЗАКРЫТОЙ смене на кассе, скорее всего, нельзя — это не проверено на живом API,
очередь такие записи придерживает и показывает на `/x2pos`.

ОФД к кассе НЕ подключён (`is_ofd_available = 0`) — `/api/ofd_receipt` не
использовать, фискальный чек с сайта не выбить.

Никогда не логируй payload заказа в клиенте X2pos — там ПД, правило то же, что
и для остального оформления.

Запуск вручную: `pnpm x2pos:sync -- --catalog --dry-run` (ещё `--stock`,
`--media`, `--force`). Кроны — `apps/admin/vercel.json`, роуты закрыты
`CRON_SECRET`. На плане Hobby Vercel Cron умеет только раз в сутки: если
проект на Hobby, нужен внешний планировщик на те же URL.

Категориальных цветов ровно ДВА: `--chart-site` / `--chart-store`, и они
ПОСЧИТАНЫ валидатором, а не подобраны. Статусные токены сериями быть не могут:
`--success` и `--water` расходятся на ΔE 7.9 при нормальном зрении. После любой
правки прогнать оба режима:
`node scripts/validate_palette.js "#b07f3c,#3a82b8" --mode dark --surface "#241f18"`

Продажи САЙТА считаются по своим заказам (`order`), а не по X2pos: заказ
доезжает туда через очередь, и счёт по X2pos занижал бы сайт ровно тогда, когда
обмен сломан. Продажи МАГАЗИНА — из X2pos, где `channel` не наш.

Долгов два, и они не сходятся: «не оплачено по продажам» (`total − total_paid`)
и «долг по карточкам клиентов» (поле `debt`). Расхождение внутреннее для X2pos,
снаружи не сводится — показывать ОБА под своими подписями, а не выбирать одно.

Роли выключены (`ENFORCE_ROLES = false` в `packages/core/src/permissions.ts`):
пользователь один. Вызовы `can()` на экранах оставлены, правило живёт в
`canByRole` и остаётся под тестами — включить обратно одной строкой.

Демо-заказы: `pnpm db:demo-orders`, удалить `-- --clean`. Они НЕ пишут в
`x2pos_outbox` — выдуманный заказ, доехавший до X2pos, спишет реальный остаток
и попадёт в бухгалтерию владельца. Реф-коды VLD, ключ `demo-`.
